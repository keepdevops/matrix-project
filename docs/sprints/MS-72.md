# MS-72: Streaming Token Accounting + Synthesis Budget Integration

## Goal
The token ledger (MS-68) only records tokens on the non-streaming HTTP path
(`agent_client_http.cpp`). The SSE streaming path (`agent_stream_llama.h`)
and synthesis budget (`synthesis_budget.cpp`) are both silent to the ledger.
This sprint closes that gap so session token totals, TES, and Prometheus
metrics reflect all traffic — not just swarm-dispatch calls.

## Background
`llama-server` emits `timings` (or `usage`) in the final SSE chunk when
streaming. The chunk has the shape:

```json
{"timings": {"tokens_evaluated": 512, "tokens_predicted": 128}, ...}
```

or the OpenAI-compat shape in the `x-token-usage` header / final `data:` line:

```json
{"usage": {"prompt_tokens": 512, "completion_tokens": 128}}
```

Both fields need to be read and forwarded to `token_ledger::add()`.

## Scope

### C++ — streaming path

- **`cpp_core/src/agent_stream_llama.h`** — in `stream_llama()`, parse the
  final SSE chunk for token counts. The last `data:` line before
  `data: [DONE]` often carries `timings` or `usage`. Extract
  `tokens_evaluated` (prompt) and `tokens_predicted` (completion), or fall
  back to `usage.prompt_tokens` / `usage.completion_tokens`. Call
  `token_ledger::add(session_context::current(), prompt_toks, completion_toks)`
  after streaming completes.

- **`cpp_core/src/agent_stream_llama.h`** — likewise for `stream_mlx_oneshot()`:
  parse `usage` from the final JSON response body and call `token_ledger::add()`.

- **`cpp_core/src/synthesis_budget.cpp`** — after the synthesis call completes
  (non-streaming HTTP), record prompt + completion tokens to the ledger using
  the existing `session_context::current()` so synthesis spend counts against
  the session budget.

### C++ — budget enforcement in streaming dispatch

- **`cpp_core/src/coordinator_routes_architect_stream.cpp`** (or its split
  header) — read `kv_pressure` from the SSE request body and set the session
  context + budget before streaming begins. After streaming ends, clear the
  session context. This mirrors what `coordinator_routes_dispatch.cpp` already
  does for the non-streaming path.

### JS — streaming response TES

- **`src/api/sseStreamReader.js`** — when the final SSE envelope arrives
  (the `data: {...}` chunk that includes `meta`), extract `meta.tes` and
  emit it via an `onTes` callback option so callers can record it.

- **`src/hooks/useOrchestrateStream.js`** (or equivalent SSE hook) — wire
  `onTes` from `sseStreamReader` into `useTesHistory.record()` so the
  sparkline updates on streaming completions too.

## Files NOT touched
- `token_ledger.h/.cpp` — no API changes needed
- `coordinator_routes_dispatch.cpp` — already handles non-streaming path
- Python test suite — no scan anchors needed

## Acceptance Criteria

2. `GET /api/metrics` reflects streaming token consumption.
3. Synthesis spend is counted (verify via coordinator stdout log line).
4. `./scripts/build_cpp_binaries.sh` — clean build.
5. 924 JS + 28 Python tests pass.
