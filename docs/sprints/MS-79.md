# MS-79: Conversation Branching — Fork from History Entry

## Goal
Allow users to fork any past conversation entry into a new independent
session. This is the "branch" operation: the new session starts with the
context of the selected history entry but diverges from there, leaving the
original session untouched.

## Background
History entries have `_run_id`, `_session_id`, `prompt`, and agent responses.
The session store (`session_store.h`) supports `session_build_continuation`
which constructs follow-up context from an existing session. A fork creates a
new `session_id`, seeds it with the selected entry's context, and returns the
new session ID to the client — which can then use `followup: true` against
the new session.

## Scope

### C++ — fork endpoint

- **`cpp_core/src/coordinator_routes_history_fork.h`** (new, inline) —
  `POST /api/history/:run_id/fork`:
  - Find the entry in `st.history` by `_run_id`.
  - Create a new `session_id` via `session_new_id("fork")`.
  - Write a synthetic session entry into `st.sessions` containing the
    forked entry's `prompt` and best agent response as prior context,
    so the next followup call has something to continue from.
  - Return `{ fork_session_id, source_run_id, prompt }`.

- **`cpp_core/src/coordinator_routes.cpp`** — register the fork route.

### JS — fork action

- **`src/api/historyApi.js`** — add `forkSession(runId)` →
  `POST /api/history/:run_id/fork`.

- **`src/hooks/useForkSession.js`** (new) — wraps `forkSession`; returns
  `{ fork, forking, forkResult, error }`. `forkResult` is
  `{ fork_session_id, prompt }` on success.

- **`src/components/ForkButton.js`** (new) — small button rendering
  a fork icon (⑂ or similar). Accepts `runId` and `onForked(result)` props.
  Shows spinner while forking, success flash on completion.

- **`src/components/HistorySearch.js`** — add `ForkButton` to each result
  row; call `onSelect` with the fork result so the parent can switch to the
  new session.

- **`src/components/ConversationTurn.js`** — add `ForkButton` next to the
  TES badge (when `entry._run_id` is present).

## Files NOT touched
- `session_store.cpp` — session append logic unchanged; fork uses
  existing `session_append_run` call pattern
- `token_ledger` — fork session starts with no budget consumed
- Python test suite — no scan anchors needed

## Acceptance Criteria
1. `POST /api/history/:run_id/fork` returns `fork_session_id`.
2. A followup with `session_id = fork_session_id` sees the forked context.
3. `ForkButton` appears in `HistorySearch` results and `ConversationTurn`.
4. Clicking Fork switches the UI to the new session.
5. `./scripts/build_cpp_binaries.sh` — clean build.
6. 924 JS + 28 Python tests pass.
