# MS-153 — Spike: RSS + parity vs HTTP (rigorous cold/warm/steady-state)

**Epic:** MS-130 research track
**Points:** 3
**Gate:** feeds MS-154 go/no-go (criterion: ≥30% tok/s improvement, steady-state)
**Date:** 2026-06-03 · Apple M3 Max
**Reproduce:** `bash scripts/build_mlx_embed.sh && MLX_ENV_PREFIX=~/miniforge3/envs/mlx-env ./build/mlx_embed/mlx_bench_probe <model> 80 6`

## Why this supersedes the MS-152 number

MS-152 reported a single figure (**85.0 tok/s, +51.8%**). That number does
not reproduce as a stable value — it was a mid-warmup snapshot. Measuring
across **separate process launches** (each reloading the model) showed wild
variance driven by OS filesystem cache state, not inference:

| Separate-process run | tok/s | vs HTTP |
|----------------------|------:|--------:|
| 1 (cold page cache) | 50.5 | **−9.8%** |
| 2 | 67.6 | +20.7% |
| 3 | 110.4 | +97.2% |
| 4 | 109.9 | +96.3% |

The 50→110 climb is the model safetensors warming into the OS page cache,
not the GPU. MS-152's 85.0 sat in the middle of this curve.

## Rigorous method (MS-153)

Load the model **once**, then run N generate iterations **in the same
process** so warmup separates from steady-state, and the model-file page
cache is irrelevant after the single load. Probe: `tests/cpp/mlx_bench_probe.cpp`.

## Results (two independent runs, 6 iterations each, 80 tokens)

| Metric | Run A | Run B |
|--------|------:|------:|
| model load (one-time) | 851.7 ms | ~850 ms |
| cold (iter 0, model resident) | 111.9 tok/s | 110.5 tok/s |
| **steady-state (median warm tail)** | **116.0 tok/s** | **116.0 tok/s** |
| RSS with model loaded | 2324 MB | 2329 MB |
| output deterministic across iters | yes | yes |

Per-iteration (Run A): 111.9 → 117.0 → 116.4 → 116.0 → 114.4 → 113.7 tok/s.

### vs HTTP baseline (56.0 tok/s, MS-150, warm)

| | tok/s | Δ |
|---|------:|--:|
| HTTP (mlx_lm.server) | 56.0 | baseline |
| in-process cold | ~111 | +98% |
| **in-process steady-state** | **116.0** | **+107%** |

## Findings

1. **Steady-state is +107%, not +51.8%.** Once the model is resident (the
   real deployment condition — a coordinator loads once at startup and keeps
   it), even the first in-process generate is ~+98%; steady-state is ~+107%.
   The decision margin over the 30% gate is far larger than MS-152 documented.

2. **The −9.8% "regression" was a cold *filesystem* cache, not slow inference.**
   It only appears on a fresh process whose model file isn't in the OS page
   cache yet — irrelevant to a persistent coordinator. Worth noting for cold-
   start latency, not for steady-state throughput.

3. **RSS ≈ 2.33 GB** for Llama-3.2-3B-4bit loaded in-process. This is the
   in-process footprint that matters for the air-gapped RAM budget: it
   *replaces* the separate `mlx_lm.server` process (which carries its own
   ~2 GB + Python interpreter), so in-process is not additive — it's a net
   wash-to-savings on total RSS while removing the HTTP hop.

4. **Output is deterministic** across iterations (greedy decode), and matches
   the HTTP path's output structurally — both call the identical
   `mlx_lm.generate()`; the embed path just removes the socket round-trip.

## MS-154 decision

**GO** — steady-state **+107%** comfortably clears the **≥30%** gate, on a
reproducible two-run measurement with documented methodology. RSS is a wash
(replaces the sidecar process, not additive). No determinism concerns.

Caveat for MS-161 scoping: the win is a single-user, non-batched, warm-model
result. Cold-start (first request after launch) is dominated by the one-time
~850 ms model load, unchanged from the HTTP path. Batched/concurrent
throughput was not measured here and should be part of MS-161's own
acceptance criteria (MS-161 currently has no issue breakdown).
