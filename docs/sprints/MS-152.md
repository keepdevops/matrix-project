# MS-152 — Spike: In-Process 4B Generate

**Epic:** MS-130 research track  
**Points:** 8  
**Branch:** `main`  
**Gate:** feeds MS-154 go/no-go (criterion: ≥30% tok/s improvement)

## Result (measured 2026-06-02, Apple M3 Max)

| Path | tok/s | Δ vs HTTP |
|------|-------|-----------|
| HTTP (mlx_lm.server via coordinator) | 56.0 | baseline |
| **In-process CPython embed** | **85.0** | **+51.8%** |

**+51.8% exceeds the 30% MS-154 gate → GO for MS-161 (in-process inference epic).**

Model: `Llama-3.2-3B-Instruct-4bit`, 80 tokens, Apple M3 Max.
Model load: 670 ms (one-time per process; amortised to ~0 in a persistent coordinator).
Generate: 953 ms for 81 tokens.

## What was built

CPython embedding wired into the MS-151 CMake infrastructure, calling
`mlx_lm.load()` + `mlx_lm.generate()` directly from a C++ binary without
any HTTP round-trips.

### Files

| File | Purpose |
|------|---------|
| `cpp_core/src/mlx_embed_generate.h` | Public API: `GenerateResult generate_via_python(...)` |
| `cpp_core/src/mlx_embed_generate.cpp` | CPython embedding: initialises interpreter, calls mlx_lm |
| `tests/cpp/mlx_generate_probe.cpp` | Probe binary; prints tok/s and GO/NO-GO vs HTTP baseline |
| `cpp_core/CMakeLists.txt` (updated) | Adds `mlx_generate_probe` target; detects Python 3.12 in mlx-env |
| `scripts/build_mlx_embed.sh` (updated) | Builds both probes; patches `@rpath/libmlx.dylib` after link |

### API

```cpp
mlx_embed::GenerateResult r = mlx_embed::generate_via_python(
    "/path/to/model",   // safetensors directory
    "Explain X.",       // prompt
    80,                 // max_tokens
    ""                  // python_home; "" → $MLX_ENV_PREFIX or ~/miniforge3/envs/mlx-env
);
// r.ok, r.n_tokens, r.load_ms, r.elapsed_ms, r.tok_s, r.output, r.error
```

## Engineering notes

### CPython embedding approach

The spike embeds Python 3.12 (`libpython3.12.dylib` from mlx-env) and calls
`mlx_lm.load()` / `mlx_lm.generate()` via `PyRun_String`. No transformer code
reimplemented in C++; all weight formats and tokenisers work automatically.
The interpreter is initialised once via `Py_InitializeFromConfig` with
`PYTHONHOME` pointing at the mlx-env prefix.

### dylib version mismatch (resolved)

Two copies of `libmlx.dylib` exist in mlx-env with different ABIs:
- `mlx-env/lib/libmlx.dylib` — older (0.31.1, `StreamOrDevice` without `ThreadLocalStream`)
- `mlx-env/lib/python3.12/site-packages/mlx/lib/libmlx.dylib` — newer (0.31.2, with `ThreadLocalStream`)

`mlx/core.cpython-312-darwin.so` requires the newer version.  CMake
auto-prepends the link-time directory to `@rpath`, causing the wrong copy to
load first at runtime.  **Fix:** `build_mlx_embed.sh` uses `install_name_tool
-change` to embed the absolute site-packages path; `CMakeLists.txt` selects
the site-packages headers+lib at compile time.

## What MS-154 should decide

The 51.8% tok/s gain is strong for a single-user, non-batched workload on M3
Max.  MS-153 should measure resident memory (RSS) of the in-process approach
vs the separate `mlx_lm.server` process to check for a memory trade-off before
committing to MS-161.
